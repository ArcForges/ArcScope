# ArcScope annotation owner composition

<!-- SPDX-License-Identifier: AGPL-3.0-only -->

`ProductComposition` owns the annotation repository and invocation journal over a borrowed, host-owned `IStore`. The host supplies the real approval coordinator, step-up coordinator, lease validator, security audit sink and invocation trace sink. Each `BindHostSession` registration supplies immutable actor identity, current actor policy, actual availability/context providers and an actor-bound decision recorder. Register the shared assistant with its own Agent chain and lease; a human endpoint cannot stand in for an Agent endpoint. Dispose the composition before disposing the store.

The production operation bindings are the published `IScopeOperations.GetSession` and `IScopeOperations.CreateAnnotation`. Internal owners are reachable through the shared invocation pipeline and final enforcement gate. Session bootstrap is a separate trusted-human operation: it requires current enabled owner-write permission and a complete validated name/configuration. An intentionally configured replay session can contain no captures; this creates metadata, not acquisition or sample evidence. Annotation history is a cloned local projection obtained through a fresh GetSession invocation and current owner/version/actor/lease checks; it is not a new wire method.

## Requests and retries

Callers retain the complete typed request and command ID for an explicit same-command retry. `ProductInvocationOptions` carries invocation/command IDs, frozen context and optional approval/lease references; it accepts no caller actor or grant claims. The command fingerprint distinguishes changed inputs. A lost response does not permit automatic redispatch: an unfinished durable invocation reservation replays an unknown effect after restart. New input uses a new command and the current expected native revision.

The operation-local codec accepts only the declared generated fields and exact schema IDs. It rejects unknown protobuf facts, duplicate or unknown record keys, invalid presence/oneof combinations and budget overflow. UUIDs use canonical lowercase GUID-D text; uint64 values use canonical unsigned decimal text across the full range; sint64 uses Integer, uint32 uses bounded Integer, authored doubles use finite Number and optional bytes use canonical padded base64 Text. It preserves all supplied session configuration/capture metadata. Record keys are ASCII and ordinal sorted; limits are 200 keys/items, depth 16 and the authored per-operation byte/node budgets. Request metadata is validated against, then derived from, trusted invocation and installation/scope/recovery evidence.

The committed annotation matcher returns internal persisted data proof only. It checks the original request envelope, normalized command fingerprint, actual receipt, exact target and original-to-committed revision transition. It grants no identity, permission, lease or approval. Owner replay must remain behind fresh final authorization and the exact per-operation approval binding.

## Durable state and failure boundaries

Annotations, owner revision and command receipt share one atomic root mutation. Lease and approval adapters use the same store writer and reject invalid CAS/lifecycle/owner transitions. The invocation journal records a reservation before dispatch and the complete typed outcome afterward; successful replay restores data through the exact registered producer binding without invoking the owner. Reservation, command fingerprint and stored version union must agree. A terminal outcome is acknowledged only after the matching durable record is observed.

Cancellation before work enters the composition has no effect. After entry, cancellation or loss of a commit acknowledgement can have an unknown effect; receipt reconciliation determines what actually committed. Cross-process contention uses store CAS and bounded backoff, while same-command in-process waiters share the reservation without canceling one another. Shutdown refuses new work, cancels host/context calls, drains admitted operations and completes unresolved journal waiters with an unknown effect. Closing a UI surface is a separate view lifecycle and must not dispose the application composition.

Storage is deliberately bounded and does not evict command receipts: a registry holds at most 16,384 records/16 MiB, a record at most 1 MiB, and a session at most 128 annotations/256 receipts. Capacity exhaustion refuses further mutation while preserving prior data. Future formats, corrupt identity/version/hash bindings and incompatible schemas refuse reads/writes; do not erase a database to make it reopen.

Formal package closure, component/Native AOT CI and delivery receipts are recorded in the APP.02 task handoff/PR. Temporary diagnostics against an incompatible dependency cohort are not accepted package or deployment evidence. Whole-system, real Cloud/device and assistive-technology acceptance are separate recorded integration obligations.
